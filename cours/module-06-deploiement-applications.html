Module 06 · Faire tourner les applications

Déployer React + Express, PHP et Python

Trois applications, trois technologies, un seul serveur. Ce module les fait tourner côte à côte : chacune avec son compte, son dossier versionné, son service, et aucune possibilité d'aller lire chez les voisines.

Module 06 Applications internes rien n'est encore public Prérequis modules 04 et 05
À ce stade, aucune application n'est accessible depuis Internet. Express et Uvicorn écoutent sur la boucle locale, PHP-FPM n'écoute même pas sur le réseau. La publication viendra au module 07, derrière Nginx et HTTPS.
Trois comptes ne suffisent pas à tout isoler. Ils séparent les responsabilités et les fichiers. Ils ne remplacent pas un conteneur : une compromission de root atteindrait les trois applications.

1. Objectif du module

À la fin de ce module, les trois applications répondent en local, chacune sous son propre compte, et aucune ne peut lire les fichiers des autres.

  • Organiser chaque application en livraisons versionnées, avec un lien current.
  • Lancer l'API Express avec un service systemd dédié.
  • Configurer un pool PHP-FPM propre à l'application PHP.
  • Créer un environnement virtuel Python et lancer Uvicorn par systemd.
  • Prouver qu'aucun compte ne peut lire les données d'une autre application.
Le lien current, à quoi ça sert ? Les applications lisent toujours /srv/apps/<app>/current. Déployer une nouvelle version revient donc à déplacer un seul lien symbolique — et le retour arrière aussi.

2. Prérequis

Ce module s'appuie sur les deux précédents.

  • Module 04 : les trois sous-domaines résolvent vers le serveur.
  • Module 05 : Nginx, PHP-FPM, Python, Node.js et MariaDB sont installés, les bases et les six comptes SQL existent.
  • Les comptes deploy-* et svc-* ainsi que les groupes reactapp, phpapp et pythonapp sont créés (module 03).
  • Le code des trois applications est disponible : dépôt Git à cloner, ou fichiers à transférer depuis votre poste.
Vérifiez les comptes avant d'écrire des fichiers. Un install -o deploy-react sur un compte inexistant échoue, et laisse l'arborescence appartenant à root — d'où des « permission denied » très difficiles à comprendre plus tard.

3. Étape 1 — Créer l'arborescence versionnée

Objectif : que chaque application ait ses dossiers, ses droits, et un point de bascule.

Action : créez les dossiers de l'application A avec les bons propriétaires.

Sur le serveur crée des dossiers

sudo install -d -m 750 -o deploy-react -g reactapp /srv/apps/react-app/releases
sudo install -d -m 750 -o deploy-react -g reactapp /srv/apps/react-app/shared
sudo install -d -m 750 -o deploy-react -g reactapp /srv/apps/react-app/releases/20261017-1010
sudo -u deploy-react ln -sfn /srv/apps/react-app/releases/20261017-1010 /srv/apps/react-app/current

Le mode 750 empêche toute autre application de traverser ce dossier : même un compte voisin qui connaît le chemin ne peut pas y entrer. Le dernier chiffre (0) retire tous les droits au reste du monde.

Action : répétez pour les applications B et C.

sudo install -d -m 750 -o deploy-php -g phpapp /srv/apps/php-app/releases
sudo install -d -m 750 -o deploy-php -g phpapp /srv/apps/php-app/shared
sudo install -d -m 750 -o deploy-php -g phpapp /srv/apps/php-app/releases/20261017-1010

sudo install -d -m 750 -o deploy-python -g pythonapp /srv/apps/python-app/releases
sudo install -d -m 750 -o deploy-python -g pythonapp /srv/apps/python-app/shared
sudo install -d -m 750 -o deploy-python -g pythonapp /srv/apps/python-app/releases/20261017-1010

Vérification : ls -ld /srv/apps/*/ /srv/apps/*/shared montre deploy-react:reactapp, deploy-php:phpapp et deploy-python:pythonapp, tous en 750.

En cas d'erreur : chown failed: invalid user signifie que le compte n'existe pas : revenez à l'étape 3 du module 03. Si une arborescence appartient déjà à root, corrigez-la avec sudo chown -R deploy-react:reactapp /srv/apps/react-app après avoir vérifié que ce dossier ne contient aucun fichier partagé.

4. Étape 2 — App A : publier React et lancer Express

Objectif : l'API Express répond sur la boucle locale, sous le compte svc-react.

Action : déployez le code dans la livraison, puis installez les dépendances.

Sur le serveur sous le compte de déploiement

sudo -u deploy-react git clone <URL_DU_DEPOT> /srv/apps/react-app/releases/20261017-1010
sudo -u deploy-react npm --prefix /srv/apps/react-app/releases/20261017-1010 ci
sudo -u deploy-react npm --prefix /srv/apps/react-app/releases/20261017-1010 run build

npm ci installe exactement les versions verrouillées, et npm run build produit le dossier dist/ : c'est du statique, que Nginx servira au module 07. L'API Express vit à côté, dans server/.

Action : créez le fichier de secrets, lisible par le service seul.

sudo install -m 640 -o root -g reactapp /dev/null /srv/apps/react-app/shared/.env
sudoedit /srv/apps/react-app/shared/.env

Dans ce fichier, renseignez les identifiants SQL du compte d'exécution :

DB_HOST=127.0.0.1
DB_PORT=3306
DB_NAME=app_react
DB_USER=user_react
DB_SECRET=<MOT_DE_PASSE_EXECUTION>

Action : créez le service, puis démarrez-le.

sudoedit /etc/systemd/system/app-react-api.service
[Unit]
Description=API Express (application React + Express)
After=network-online.target mariadb.service

[Service]
User=svc-react
Group=reactapp
WorkingDirectory=/srv/apps/react-app/current/server
EnvironmentFile=/srv/apps/react-app/shared/.env
ExecStart=/usr/bin/node /srv/apps/react-app/current/server/index.js
Restart=on-failure
NoNewPrivileges=true
PrivateTmp=true

[Install]
WantedBy=multi-user.target
command -v node
sudo systemctl daemon-reload
sudo systemctl enable --now app-react-api
systemctl status app-react-api --no-pager
curl -sS http://127.0.0.1:3001/health

User=svc-react fait tourner le processus sous le compte d'exécution. EnvironmentFile charge les secrets sans les mettre dans la ligne de commande. command -v node vérifie le chemin exact du binaire : corrigez ExecStart s'il diffère.

Vérification : systemctl status indique active (running) et curl renvoie la réponse de /health. ss -lntp montre Express sur 127.0.0.1 seulement.

En cas d'erreur : status=203/EXEC veut dire que le binaire d'ExecStart est introuvable : comparez avec command -v node. status=200/CHDIR : le dossier de travail n'existe pas — vérifiez que current pointe bien vers une livraison. Les messages du service sont dans journalctl -u app-react-api -n 50.

Ne lancez jamais l'API avec --host 0.0.0.0 ni en écoutant sur toutes les interfaces. Un port applicatif visible depuis Internet contourne Nginx, son HTTPS et ses journaux.

5. Étape 3 — App B : PHP natif + PDO

Objectif : un pool PHP-FPM qui exécute uniquement le code de l'application PHP.

Action : déployez le code, puis créez un pool dédié.

Sur le serveur configure un service

sudo -u deploy-php git clone <URL_DU_DEPOT> /srv/apps/php-app/releases/20261017-1010
sudo -u deploy-php ln -sfn /srv/apps/php-app/releases/20261017-1010 /srv/apps/php-app/current
sudo install -m 640 -o root -g phpapp /dev/null /srv/apps/php-app/shared/.env
sudoedit /etc/php/8.4/fpm/pool.d/app-php.conf
[app-php]
user = svc-php
group = phpapp
listen = /run/php/app-php.sock
listen.owner = www-data
listen.group = www-data
listen.mode = 0660
pm = dynamic
pm.max_children = 8

Le pool écoute sur un socket de fichier, pas sur un port réseau : aucun programme extérieur ne peut s'y connecter. Le pm.max_children limite le nombre de processus PHP simultanés, ce qui évite qu'une application gourmande asphyxie le serveur. 

sudo /usr/sbin/php-fpm8.4 -t
sudo systemctl restart php8.4-fpm
ls -l /run/php/app-php.sock
ss -lntp

Vérification : php-fpm8.4 -t ne signale aucune erreur, le fichier /run/php/app-php.sock existe, et ss -lntp ne montre aucun port PHP : c'est le comportement attendu.

En cas d'erreur : ERROR: [pool app-php] cannot get uid of user 'svc-php' signifie que le compte n'existe pas. Un socket absent après un restart indique une erreur de configuration : journalctl -u php8.4-fpm -n 50 donne la ligne exacte. Adaptez 8.4 à la version affichée par php -v.

6. Étape 4 — App C : FastAPI + Uvicorn

Objectif : une API Python isolée dans son environnement virtuel, lancée par systemd.

Action : déployez le code, puis créez l'environnement virtuel.

Sur le serveur sous le compte d'exécution

sudo -u deploy-python git clone <URL_DU_DEPOT> /srv/apps/python-app/releases/20261017-1010
sudo -u deploy-python ln -sfn /srv/apps/python-app/releases/20261017-1010 /srv/apps/python-app/current
sudo install -d -m 750 -o svc-python -g pythonapp /srv/apps/python-app/venv
sudo -u svc-python python3 -m venv /srv/apps/python-app/venv
sudo -u svc-python /srv/apps/python-app/venv/bin/pip install -r /srv/apps/python-app/current/app/requirements.txt

L'environnement virtuel isole les dépendances Python du système : rien ne vient modifier les paquets Debian. Comme il appartient à svc-python, c'est le compte d'exécution qui peut les installer et les lire.

Action : créez le service.

sudoedit /etc/systemd/system/app-python-web.service
[Unit]
Description=API FastAPI (application Python)
After=network-online.target mariadb.service

[Service]
User=svc-python
Group=pythonapp
WorkingDirectory=/srv/apps/python-app/current
EnvironmentFile=/srv/apps/python-app/shared/.env
ExecStart=/srv/apps/python-app/venv/bin/uvicorn app.main:app --host 127.0.0.1 --port 8000
Restart=on-failure
NoNewPrivileges=true
PrivateTmp=true

[Install]
WantedBy=multi-user.target
sudo install -m 640 -o root -g pythonapp /dev/null /srv/apps/python-app/shared/.env
sudo systemctl daemon-reload
sudo systemctl enable --now app-python-web
systemctl status app-python-web --no-pager
curl -sS http://127.0.0.1:8000/health

--host 127.0.0.1 est essentiel : sans lui, Uvicorn écouterait sur toutes les interfaces. app.main:app désigne le module et l'objet de l'application FastAPI.

Vérification : le service est active (running), curl renvoie la réponse de /health, et ss -lntp montre Uvicorn sur 127.0.0.1 uniquement.

En cas d'erreur : ModuleNotFoundError signifie que les dépendances n'ont pas été installées dans ce venv : vérifiez le chemin utilisé dans la commande pip. upstream connect error ou une réponse vide vient plutôt de l'application elle-même : lisez journalctl -u app-python-web -n 50.

7. Étape 5 — Vérifier l'isolation entre les applications

Objectif : prouver, plutôt que supposer, que les comptes sont bien séparés.

Action : tentez volontairement des accès interdits. Chacun doit échouer.

Sur le serveur test de sécurité

sudo -u deploy-react cat /srv/apps/php-app/shared/.env
sudo -u deploy-php touch /srv/apps/react-app/current/dist/x
sudo -u deploy-python cat /srv/apps/react-app/shared/.env
sudo -l -U deploy-react
Ces commandes doivent échouer. Si l'une d'elles affiche un secret ou réussit une écriture, votre configuration est fausse : ne continuez pas. Corrigez les propriétaires et les modes du dossier concerné avant tout déploiement.

Vérification : les trois premières commandes renvoient Permission denied, et sudo -l -U deploy-react refuse en indiquant que cet utilisateur n'a aucun droit sudo.

En cas d'erreur : sudo: a password is required sur sudo -u signifie que votre propre compte n'a pas de droit d'administration. Une lecture réussie de .env par un compte voisin indique un mode trop permissif : l'objectif reste 640 root:<groupe-app>.

8. Problèmes courants

Symptôme, cause probable, action.

Problèmes courants : symptôme, cause probable et action
SymptômeCause probableQue faire
status=203/EXEC Binaire introuvable dans ExecStart Comparez avec command -v node ou le chemin du venv
status=200/CHDIR Dossier de travail inexistant Vérifiez que le lien current pointe vers une livraison
status=226/NAMESPACE Option de confinement incompatible avec un chemin utilisé Retirez temporairement PrivateTmp, puis diagnostiquez
Le service redémarre en boucle Erreur au démarrage de l'application (port occupé, variable manquante) journalctl -u <service> -n 50 donne la cause exacte
Pas de socket PHP-FPM Pool invalide, ou version PHP différente de celle du chemin php-fpm8.4 -t, puis journalctl -u php8.4-fpm
Permission denied en lecture de fichiers Un compte exécute un fichier qu'il ne peut pas lire Contrôlez le mode de chaque niveau avec namei -l

9. Checklist finale

Ce module est terminé lorsque les huit points suivants sont vrais.

  • Les trois arborescences existent sous /srv/apps/, en 750, avec le bon propriétaire.
  • Chaque application a un lien current vers une livraison horodatée.
  • Les trois services sont active (running) et enabled.
  • Express et Uvicorn écoutent sur 127.0.0.1 uniquement.
  • PHP-FPM utilise un socket de fichier, et aucun port PHP n'apparaît dans ss -lntp.
  • Les fichiers .env sont en 640 root:<groupe-app>.
  • Les tests d'accès croisés échouent tous, comme attendu.
  • Aucun port applicatif n'a été ouvert dans le pare-feu.
Et ensuite ? Le module 07 publie les trois applications derrière Nginx, avec un certificat HTTPS par domaine et une redirection automatique.
