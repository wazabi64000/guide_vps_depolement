Module 07 · Ouvrir au monde, proprement

Configurer Nginx et HTTPS

Les applications tournent, mais restent invisibles. Ce module donne à chacune son domaine, laisse Nginx distribuer le trafic, et couvre le tout d'un certificat Let's Encrypt renouvelé automatiquement.

Module 07 Met en ligne les applications deviennent publiques Prérequis modules 04 et 06
À partir de ce module, votre serveur est visible sur Internet. Ne publiez qu'un serveur que vous administrez, avec un pare-feu correctement réglé (module 03) et aucune donnée personnelle d'autrui.
Valeurs fictives. app-react.exemple.fr, 192.0.2.10 et 2001:db8::10 sont des exemples réservés à la documentation (RFC 2606, RFC 5737, RFC 3849). Remplacez-les par vos noms et adresses réels.

1. Objectif du module

À la fin de ce module, les trois applications répondent en HTTPS sur leur domaine, et HTTP renvoie vers HTTPS sans exception.

  • Écrire un hôte Nginx par domaine, dans sites-available/.
  • Servir le build React, l'API Express et l'API Python par proxy, et le site PHP par PHP-FPM.
  • Obtenir un certificat Let's Encrypt avec Certbot.
  • Rediriger tout le HTTP vers HTTPS.
  • Prouver que le renouvellement fonctionnera sans intervention.
Pourquoi Nginx devant les applications ? Pour trois raisons : un seul endroit gère les certificats, les applications n'écoutent plus que sur la boucle locale, et chaque requête est journalisée au même format.

2. Prérequis

Trois conditions à réunir.

  • Module 04 : les trois sous-domaines résolvent bien vers le serveur, en IPv4 et en IPv6.
  • Module 06 : les trois applications répondent en local (Express sur 3001, Uvicorn sur 8000, socket PHP-FPM présent).
  • Le pare-feu (module 03) autorise 80 et 443 en IPv4 et en IPv6.
Certbot a besoin du port 80. L'obtention du certificat passe par une vérification sur 80 (HTTP) ou 443. Un port fermé en IPv6 alors qu'il est ouvert en IPv4 peut faire échouer le renouvellement sans message clair : vérifiez les deux familles avant de commencer.

3. Étape 1 — Écrire un hôte Nginx par domaine

Objectif : chaque domaine a son fichier de configuration, indépendant des autres.

Action : sauvegardez la configuration actuelle, puis créez le premier hôte.

Sur le serveur modifie la configuration

sudo tar czf ~/nginx-avant-https.tgz /etc/nginx
sudoedit /etc/nginx/sites-available/app-react.exemple.fr.conf

Contenu de l'hôte pour l'application A :

server {
    listen 80;
    listen [::]:80;
    server_name app-react.exemple.fr;

    root /srv/apps/react-app/current/dist;
    index index.html;

    location /api/ {
        proxy_pass http://127.0.0.1:3001/;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
    }

    location / {
        try_files $uri /index.html;
    }

    access_log /var/log/nginx/app-react.access.log;
    error_log  /var/log/nginx/app-react.error.log;
}

listen est écrit deux fois : une ligne pour IPv4, une pour IPv6. Le bloc location /api/ envoie les appels d'API vers Express, le reste sert le build React. Les en-têtes X-Real-IP et X-Forwarded-Proto transmettent à l'application l'adresse réelle du visiteur et le protocole d'origine. 

sudo ln -s /etc/nginx/sites-available/app-react.exemple.fr.conf /etc/nginx/sites-enabled/
sudo nginx -t

Vérification : nginx -t répond syntax is ok et test is successful. Si ce n'est pas le cas, ne rechargez pas : Nginx fonctionne encore avec l'ancienne configuration.

En cas d'erreur : duplicate default server vient de l'hôte par défaut fourni par Debian. could not build server_names indique un nom mal recopié. Corrigez, relancez nginx -t, puis seulement sudo systemctl reload nginx.

4. Étape 2 — Servir les trois applications

Objectif : chaque technologie reçoit la configuration qui lui correspond.

Action : créez l'hôte du site PHP. Seul son dossier public/ est exposé.

server {
    listen 80;
    listen [::]:80;
    server_name app-php.exemple.fr;

    root /srv/apps/php-app/current/public;
    index index.php;

    location / {
        try_files $uri $uri/ /index.php?$query_string;
    }

    location ~ \.php$ {
        include snippets/fastcgi-php.conf;
        fastcgi_pass unix:/run/php/app-php.sock;
    }

    location ~ /\.(?!well-known) {
        deny all;
    }
}

fastcgi_pass désigne le socket créé au module 06 : le code PHP n'est jamais exécuté par Nginx lui-même. Le dernier bloc refuse l'accès aux fichiers commençant par un point (hors .well-known, nécessaire aux certificats).

Action : créez l'hôte de l'API Python.

server {
    listen 80;
    listen [::]:80;
    server_name app-python.exemple.fr;

    location / {
        proxy_pass http://127.0.0.1:8000;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
    }
}
sudo ln -s /etc/nginx/sites-available/app-php.exemple.fr.conf /etc/nginx/sites-enabled/
sudo ln -s /etc/nginx/sites-available/app-python.exemple.fr.conf /etc/nginx/sites-enabled/
sudo nginx -t
sudo systemctl reload nginx

Vérification : depuis votre poste local, curl -I http://app-react.exemple.fr, puis les deux autres domaines, renvoient un code 200. Une réponse 502 signifie que l'application n'écoute pas sur le port ou le socket indiqué.

En cas d'erreur : 502 Bad Gateway : vérifiez proxy_pass et fastcgi_pass avec ss -lntp et ls -l /run/php/. 403 Forbidden sur une page PHP : le dossier public/ n'est pas lisible par www-data — il doit être en 755 (module 06).

5. Étape 3 — Obtenir les certificats avec Certbot

Objectif : un certificat valide et reconnu par les navigateurs, sans configuration manuelle.

Action : installez Certbot et son greffon Nginx.

Sur le serveur installe des paquets

sudo apt install certbot python3-certbot-nginx

Action : demandez les trois certificats en une seule fois.

sudo certbot --nginx -d app-react.exemple.fr -d app-php.exemple.fr -d app-python.exemple.fr

Certbot prouve à Let's Encrypt que vous contrôlez ces noms de domaine, puis modifie vos fichiers Nginx : il ajoute le bloc 443, les chemins du certificat et la redirection depuis 80. Laissez-le faire, puis relisez le fichier obtenu : vous devez comprendre ce qui y a été ajouté.

Vérification : sudo certbot certificates liste les trois certificats avec une date d'expiration lointaine. Dans le navigateur, le cadenas apparaît et aucun avertissement n'est affiché.

En cas d'erreur : un échec de vérification vient presque toujours de la résolution DNS ou du port 80. Timeout during connect : vérifiez qu'aucun autre service ne prend le port, et que le pare-feu laisse passer 80 en IPv6 aussi. Trop de tentatives échouées : attendez avant de réessayer, l'autorité limite le nombre d'essais.

Limite à connaître. Un certificat protège le transport, pas l'application. Une faille dans votre code reste une faille, même en HTTPS.

6. Étape 4 — Forcer la redirection HTTP vers HTTPS

Objectif : qu'aucun visiteur ne reste en clair, même s'il tape http://.

Action : vérifiez que la redirection est bien en place dans chaque hôte.

sudo grep -n "return 301" /etc/nginx/sites-enabled/app-*.conf

Certbot ajoute une règle du type return 301 https://$host$request_uri; dans le bloc listen 80. Le code 301 est une redirection permanente : les navigateurs et moteurs de recherche mémoriseront l'adresse HTTPS. 

curl -sSI http://app-react.exemple.fr
curl -sSI https://app-react.exemple.fr

Vérification : la requête en http:// renvoie 301 avec un en-tête Location vers https://, et la requête en https:// renvoie 200. Testez les trois domaines, depuis l'extérieur de votre réseau.

En cas d'erreur : si http:// répond 200 au lieu de 301, la redirection manque : relancez sudo certbot --nginx en choisissant l'option de redirection. Une page 404 en HTTPS indique que le nom de domaine testé ne correspond à aucun server_name.

HSTS : à décider, pas à copier. L'en-tête Strict-Transport-Security interdit au navigateur toute connexion en clair future. C'est efficace, mais difficile à annuler : ne l'activez qu'après avoir vérifié que tous vos sous-domaines sont en HTTPS.

7. Étape 5 — Vérifier le renouvellement

Objectif : qu'un certificat expiré ne soit jamais un incident.

Un certificat Let's Encrypt dure 90 jours : le renouvellement doit être automatique et vérifié.

Action : simulez un renouvellement complet, puis contrôlez la minuterie.

Sur le serveur simulation

sudo certbot renew --dry-run
systemctl list-timers certbot.timer --no-pager
sudo systemctl status certbot.timer --no-pager

--dry-run fait tout le travail sauf remplacer réellement le certificat : c'est le seul test qui prouve que le renouvellement fonctionnera. Les paquets Debian installent une minuterie systemd (certbot.timer) qui tente le renouvellement deux fois par jour ; un certificat n'est remplacé que s'il approche de l'expiration.

Vérification : --dry-run se termine par Congratulations, all simulated renewals succeeded, la minuterie est active, et sudo certbot certificates montre les trois certificats.

En cas d'erreur : un --dry-run qui échoue alors que l'obtention avait réussi indique un changement côté réseau (DNS, pare-feu, port occupé) : comparez avec les conditions de l'étape 3. sudo journalctl -u certbot contient le détail de la dernière tentative.

9. Checklist finale

Ce module est terminé lorsque les huit points suivants sont vrais.

  • Chaque domaine a son fichier dans sites-available/, lié dans sites-enabled/.
  • Chaque hôte écoute sur IPv4 et sur IPv6.
  • nginx -t est vert, et la sauvegarde ~/nginx-avant-https.tgz existe.
  • Les trois domaines répondent en https:// avec un code 200.
  • http:// renvoie systématiquement 301 vers https://.
  • Les applications n'écoutent que sur la boucle locale.
  • certbot renew --dry-run réussit pour les trois certificats.
  • La décision concernant HSTS est prise et écrite, pas laissée au hasard.
Et ensuite ? Le module 08 remet de l'ordre dans le code : dépôts, branches, environnements séparés et secrets hors de Git.
