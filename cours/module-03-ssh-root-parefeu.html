Module 03 · Réduire la surface d'attaque

Sécuriser SSH, les comptes et le pare-feu

Un serveur neuf accepte souvent un mot de passe et parfois une connexion directe de root. Ce module passe à l'authentification par clé, crée les comptes qui déploieront les applications, et ferme tout le reste avec un pare-feu qui filtre IPv4 et IPv6.

Module 03 Risque d'enfermement lisez la procédure de retour arrière Prérequis module 02
Le risque réel de ce module : perdre l'accès au serveur. Toute modification de SSH ou du pare-feu se fait avec une seconde session déjà ouverte et, idéalement, avec la console de secours de l'hébergeur à portée de main. Ne fermez jamais la session qui fonctionne avant d'avoir validé la nouvelle.
Valeurs fictives. admin@192.0.2.10 et le port 22 sont des exemples (RFC 5737). Adaptez-les à votre machine ; si votre hébergeur fournit un port SSH différent, ne le fermez pas par erreur.

1. Objectif du module

À la fin de ce module, l'accès au serveur est nominatif et chiffré, les comptes applicatifs existent, et seuls SSH, HTTP et HTTPS sont joignables depuis Internet.

  • Authentifier l'administrateur par clé, sans mot de passe.
  • Désactiver la connexion SSH directe de root, après vérification.
  • Créer les comptes deploy-* (déploiement, sans sudo) et svc-* (exécution, sans connexion).
  • Filtrer le réseau avec nftables, en IPv4 comme en IPv6.
  • Documenter le retour arrière avant d'appliquer quoi que ce soit.
Pourquoi séparer déployer et exécuter ? Le compte qui écrit les fichiers n'est pas celui qui fait tourner le service. Une faille dans l'application ne donne donc pas le droit de modifier son propre code.

2. Prérequis

Le module 02 doit être terminé.

  • Le compte administrateur nominatif fonctionne et sudo est validé.
  • Vous disposez d'un client SSH sur votre poste local (ssh -V répond).
  • La console de secours de l'hébergeur est ouverte dans un onglet : c'est votre seul retour si le pare-feu se referme.
Notez votre configuration actuelle avant de la modifier. Un cp de sauvegarde et une copie de sudo nft list ruleset dans un fichier local vous éviteront bien des sueurs.

3. Étape 1 — Passer à l'authentification par clé

Objectif : se connecter sans mot de passe, avec une clé qui ne quitte jamais le poste local.

Action : générez une paire de clés sur votre poste local.

Poste local utilisateur : vous

ssh-keygen -t ed25519 -C "poste-local-admin"

ssh-keygen crée deux fichiers : une clé privée (qui reste chez vous, protégée par une phrase secrète) et une clé publique (.pub) qui, elle, peut être copiée sur le serveur.

Action : installez la clé publique sur le serveur.

Poste local modifie le serveur

ssh-copy-id -i ~/.ssh/id_ed25519.pub admin@192.0.2.10
N'exécutez jamais un bloc copié dans ce module sans l'avoir compris. Le retour arrière de cette étape consiste simplement à supprimer la ligne ajoutée par ssh-copy-id dans ~/.ssh/authorized_keys du compte concerné.

Vérification : testez explicitement l'authentification par clé, sans mot de passe : ssh -o PreferredAuthentications=publickey admin@192.0.2.10 whoami doit afficher admin.

En cas d'erreur : Permission denied (publickey) signifie que la clé publique n'a pas atteint authorized_keys ou que les droits du dossier ~/.ssh sont trop ouverts : sur le serveur, chmod 700 ~/.ssh et chmod 600 ~/.ssh/authorized_keys. ssh-copy-id: command not found : le paquet openssh-client est incomplet sur votre poste.

4. Étape 2 — Durcir sshd sans se couper l'accès

Objectif : interdire la connexion directe de root et l'authentification par mot de passe.

Action : lisez d'abord la configuration effective, puis sauvegardez-la.

Sur le serveur lecture seule

sudo sshd -T | grep -Ei 'permitrootlogin|passwordauthentication|pubkeyauthentication'
sudo cp -a /etc/ssh/sshd_config /etc/ssh/sshd_config.avant-durcissement

sshd -T affiche la configuration réellement appliquée, après fusion de tous les fichiers inclus : bien plus fiable qu'une lecture du fichier, où une directive peut être commentée puis redéfinie ailleurs.

Action : éditez la configuration, puis testez-la avant de recharger.

Sur le serveur modifie la machine

sudoedit /etc/ssh/sshd_config

Les trois directives à obtenir explicitement :

PermitRootLogin no
PasswordAuthentication no
PubkeyAuthentication yes
sudo sshd -t
sudo systemctl reload ssh

sshd -t valide la syntaxe sans rien appliquer : s'il ne dit rien, la configuration est acceptée. Le reload (et non restart) ne coupe pas les sessions déjà établies.

Vérification : ouvrez une nouvelle session avec votre clé. Elle doit fonctionner. Puis vérifiez sudo sshd -T filtré sur permitrootlogin et passwordauthentication : les valeurs doivent être no.

Retour arrière. Si la nouvelle session ne s'ouvre plus, utilisez la session encore ouverte (ou la console de secours) pour restaurer : sudo cp -a /etc/ssh/sshd_config.avant-durcissement /etc/ssh/sshd_config puis sudo systemctl reload ssh.

En cas d'erreur : Bad configuration option ou line N: Bad yes/no argument vient de sshd -t : corrigez la ligne indiquée avant de recharger. Un reload refusé laisse la configuration précédente en place : vous n'avez rien perdu.

5. Étape 3 — Comptes de déploiement et d'exécution

Objectif : créer trois paires de comptes séparées, sans aucun droit d'administration.

Action : créez les comptes de l'application A (React + Express).

Sur le serveur modifie la machine

sudo groupadd reactapp
sudo adduser --disabled-password --gecos "" deploy-react
sudo adduser --system --no-create-home --shell /usr/sbin/nologin --ingroup reactapp svc-react
sudo usermod -aG reactapp deploy-react

deploy-react déploie : il garde un shell interactif et des permissions limitées à /srv/apps/react-app. svc-react exécute : aucun shell (nologin), aucune clé SSH. Les deux partagent le groupe reactapp.

Action : répétez pour les deux autres applications.

sudo groupadd phpapp
sudo adduser --disabled-password --gecos "" deploy-php
sudo adduser --system --no-create-home --shell /usr/sbin/nologin --ingroup phpapp svc-php
sudo usermod -aG phpapp deploy-php

sudo groupadd pythonapp
sudo adduser --disabled-password --gecos "" deploy-python
sudo adduser --system --no-create-home --shell /usr/sbin/nologin --ingroup pythonapp svc-python
sudo usermod -aG pythonapp deploy-python
id deploy-react
sudo -l -U deploy-react
getent group reactapp phpapp pythonapp

Vérification : id deploy-react liste reactapp mais pas sudo. sudo -l -U deploy-react ne doit proposer aucune commande. Installez ensuite une clé distincte par compte de déploiement, avec ssh-copy-id — jamais la même clé partout.

En cas d'erreur : group reactapp already exists est sans gravité, le groupe est déjà créé. user already exists de même. Retour arrière d'un compte : sudo deluser --remove-home deploy-react (le compte de déploiement n'a pas de fichiers système).

Limite à connaître. Trois comptes séparés réduisent les risques, mais ne constituent pas une isolation complète : sans conteneur ni machine virtuelle, une compromission de root atteint les trois applications.

6. Étape 4 — Écrire le pare-feu nftables

Objectif : ne laisser entrer que SSH, HTTP et HTTPS — en IPv4 comme en IPv6.

nftables est le pare-feu natif de Debian. Une table inet traite les deux familles d'adresses dans un seul jeu de règles : impossible d'oublier IPv6.

Action : écrivez le fichier de règles, sauvegardez-le, puis vérifiez sa syntaxe sans l'appliquer.

Sur le serveur modifie la machine

sudo cp -a /etc/nftables.conf /etc/nftables.conf.avant-durcissement
sudo nft list ruleset | tee ~/nft-avant.txt
sudoedit /etc/nftables.conf

Contenu à écrire (adaptez le port SSH si le vôtre diffère) :

#!/usr/sbin/nft -f
flush ruleset

table inet filter {
  chain input {
    type filter hook input priority filter; policy drop;

    iif "lo" accept
    ct state established,related accept
    ct state invalid drop

    ip protocol icmp accept
    ip6 nexthdr ipv6-icmp accept

    tcp dport 22 accept
    tcp dport { 80, 443 } accept
  }

  chain forward {
    type filter hook forward priority filter; policy drop;
  }

  chain output {
    type filter hook output priority filter; policy accept;
  }
}
sudo nft -c -f /etc/nftables.conf
sudo systemctl enable --now nftables
sudo nft list ruleset

Chaque ligne compte : policy drop refuse par défaut, donc tout ce qui n'est pas explicitement accepté est bloqué. iif "lo" laisse passer la boucle locale, ct state established,related autorise les réponses aux connexions déjà ouvertes — sans quoi votre session SSH mourrait au premier paquet sortant.

Vérification : sudo nft -c -f doit rester muet (syntaxe correcte). Après application, sudo nft list ruleset montre la table inet filter, et votre session SSH tient toujours.

Retour arrière. Si vous perdez SSH, reconnectez-vous par la console de secours de l'hébergeur puis exécutez : sudo nft flush ruleset (vide les règles en mémoire) et sudo systemctl disable nftables (empêche leur retour au prochain démarrage). Vous pourrez ensuite corriger le fichier.

En cas d'erreur : une erreur de syntaxe signalée par nft -c empêche l'application : corrigez la ligne indiquée, rien n'a été chargé. Si vous avez modifié le port SSH dans sshd_config sans adapter tcp dport, vous vous enfermez dehors : gardez toujours la console de secours accessible.

7. Étape 5 — Vérifier en IPv4 et en IPv6

Objectif : s'assurer qu'aucun service interne n'est joignable, quelle que soit la famille d'adresses.

Action : relevez ce qui écoute réellement.

Sur le serveur lecture seule

ss -lntup
ip -br address
ip -6 addr

Action : comparez avec ce que le pare-feu autorise.

sudo nft list ruleset
sudo nft list chain inet filter input

Vérification : seuls 22, 80 et 443 sont ouverts. Les services internes (base de données, administration, ports applicatifs) n'apparaissent pas sur une interface publique, ni en IPv4 ni en IPv6.

Le piège classique. Un service qui écoute sur :: est joignable en IPv6 même si une règle IPv4 le bloque. Fermer un port en IPv4 ne protège donc pas : vérifiez toujours les deux familles avec ss -lntup.

En cas d'erreur : si un service apparaît sur une adresse publique, il n'a pas été lié à la boucle locale. Cela se corrige dans sa configuration, pas dans le pare-feu : c'est l'objet des modules 05 et 06.

8. Problèmes courants

Symptôme, cause probable, action.

Problèmes courants : symptôme, cause probable et action
SymptômeCause probableQue faire
Permission denied (publickey) Clé absente de authorized_keys, ou droits trop ouverts sur ~/.ssh Vérifiez le contenu et les droits : 700 sur le dossier, 600 sur le fichier
SSH répond mais la session se ferme après le pare-feu Le trafic sortant établi n'est pas autorisé Vérifiez la règle ct state established,related accept
Impossible de se reconnecter après activation du pare-feu Le port SSH réel n'est pas celui autorisé Console de secours, sudo nft flush ruleset, puis corrigez tcp dport
Une page web reste inaccessible depuis l'extérieur Rien n'écoute encore sur 80/443, ou IPv6 seule est filtrée Module 05 pour l'installation ; vérifiez les deux familles avec ss -lntup
useradd: group 'phpapp' does not exist L'ordre des commandes a été inversé Créez le groupe groupadd avant adduser --ingroup
Un service refuse de démarrer sous svc-* Le shell nologin est bien volontaire : le compte ne doit pas ouvrir de session Un service n'a pas besoin de shell : c'est le rôle de User= dans systemd (module 06)

9. Checklist finale

Ce module est terminé lorsque les sept points suivants sont vrais.

  • L'authentification par clé fonctionne pour le compte administrateur nominatif.
  • sshd -T confirme permitrootlogin no et passwordauthentication no.
  • Une sauvegarde de sshd_config et du règles précédentes existe.
  • Les six comptes deploy-* et svc-* existent, avec une clé distincte par compte de déploiement.
  • sudo -l -U ne donne aucun droit d'administration aux comptes de déploiement.
  • Le pare-feu n'est actif que sur 22, 80 et 443, en IPv4 et en IPv6.
  • La procédure de retour arrière est écrite et testée (console de secours accessible).
Et ensuite ? Le module 04 rattache les noms de domaine au serveur et choisit un mode d'accès distant — utile surtout en serveur à domicile, derrière une box.
