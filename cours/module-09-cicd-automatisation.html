Module 09 · Faire le travail une fois, pour toujours

Automatiser les déploiements avec CI/CD

Vous savez déployer à la main. Ce module transforme ces gestes en un pipeline qui teste, construit, publie et sait revenir en arrière — sans jamais donner de privilèges supplémentaires au compte de déploiement.

Module 09 Automatise ce qui était manuel Prérequis modules 06 et 08
Un pipeline qui peut déployer est un pipeline qui peut casser. Deux protections sont obligatoires, dès le premier jour : les tests bloquent le déploiement, et le retour arrière est testé, pas seulement prévu.
Ce que ce module ne fait pas. Il ne décrète pas une forge. Les exemples de fichier de workflow utilisent la syntaxe GitHub Actions, citée comme exemple : les principes (étapes, secret, concurrence, conditions) se transposent, les noms d'actions et les clés YAML, non.

1. Objectif du module

À la fin de ce module, une modification relue et fusionnée se retrouve en production après avoir traversé tests, build et déploiement — et vous savez la retirer en moins de deux minutes.

  • Écrire un pipeline par application, avec un ordre fixe : tests, build, déploiement.
  • Créer une clé de déploiement dédiée, sans droit sudo.
  • Déployer dans une nouvelle livraison, puis basculer le lien current.
  • Exécuter les migrations MariaDB avec un compte dédié, après une sauvegarde.
  • Tester le retour arrière : le basculer doit toujours fonctionner.
Le principe qui gouverne tout le module. Le pipeline ne fait que répéter sans réfléchir ce que vous avez déjà réussi à faire à la main. Si vous ne savez pas déployer manuellement, l'automatiser ne fera qu'accélérer vos erreurs.

2. Prérequis

L'automatisation s'appuie sur ce qui fonctionne déjà.

  • Module 08 : les trois dépôts existent, avec une branche principale protégée.
  • Module 06 : les livraisons versionnées et le lien current sont en place.
  • Les services (Express, Uvicorn, PHP-FPM) répondent en local.
  • Une sauvegarde récente de chaque base existe — le module 10 formalise la méthode, mais une sauvegarde manuelle avant migration est obligatoire ici.
Aucun pipeline ne s'écrit sur un serveur déjà en incident. Si une application ne démarre pas correctement à la main, réparez-la d'abord : automatiser un état instable ne fait que rendre la panne reproductible.

3. Étape 1 — Un pipeline par application

Objectif : trois pipelines indépendants, chacun avec le même ordre d'étapes.

Les trois étapes d'un pipeline et ce qu'elles garantissent
ÉtapeQuandCe qu'elle garantitSi elle échoue
VérifierÀ chaque proposition de modificationLe code compile, les tests passentRien n'est déployé
ConstruireAprès vérification réussieLes fichiers à publier existentRien n'est déployé
DéployerSur la branche principale uniquementUne nouvelle livraison est publiéeLa livraison précédente reste active

Action : créez le fichier de workflow de l'application A dans le dépôt.

name: app-react

on:
  pull_request:
  push:
    branches: [main]

concurrency:
  group: app-react-${{ github.ref }}
  cancel-in-progress: true

jobs:
  verifier:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - run: npm ci
      - run: npm run lint
      - run: npm test
      - run: npm run build

  deployer:
    needs: verifier
    if: github.ref == 'refs/heads/main'
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - run: npm ci
      - run: npm run build
      - name: Installer la clé de déploiement
        env:
          CLE: ${{ secrets.DEPLOY_SSH_KEY_REACT }}
        run: |
          install -m 700 -d ~/.ssh
          printf '%s\n' "$CLE" > ~/.ssh/deploy_react
          chmod 600 ~/.ssh/deploy_react
      - name: Déployer
        run: bash scripts/deploy-react.sh

needs: verifier crée la dépendance : deployer ne commence pas si verifier a échoué. if: github.ref == 'refs/heads/main' empêche tout déploiement depuis une branche de travail. concurrency annule l'exécution précédente devenue inutile : deux déploiements simultanés sur la même application se marcheraient dessus.

Vérification : une proposition de modification déclenche le pipeline, l'étape verifier s'exécute, et l'étape deployer est ignorée, avec la mention « skipped ».

En cas d'erreur : si l'étape deployer se lance sur une branche de travail, la condition est mal écrite. Si l'étape verifier échoue alors que les tests passent en local, la différence vient de l'environnement d'exécution : comparez la version du langage et les variables d'environnement définies des deux côtés.

4. Étape 2 — Une clé de déploiement, aucun sudo

Objectif : que le pipeline puisse écrire dans son application, et rien d'autre.

Le pipeline se connecte en deploy-react, avec une clé dédiée, distincte de la vôtre. Ce compte appartient déjà au groupe de l'application et possède son dossier : il n'a donc besoin d'aucun droit d'administration pour publier. C'est la décision du référentiel : aucune entrée sudoers n'est créée pour les comptes deploy-*.

Action : générez la paire de clés sur votre poste, puis installez la clé publique sur le serveur.

Poste local puis serveur

ssh-keygen -t ed25519 -C "pipeline app-react" -f ~/.ssh/deploy_react -N ""
ssh-copy-id -i ~/.ssh/deploy_react.pub deploy-react@app-react.exemple.fr

-N "" crée une clé sans phrase secrète : c'est acceptable ici parce que la clé privée ne vit pas sur votre poste mais dans les secrets du pipeline. La clé privée ~/.ssh/deploy_react sera copiée dans le secret DEPLOY_SSH_KEY_REACT, puis supprimée de votre poste.

Une clé de pipeline est un secret d'accès direct au serveur. Elle doit être : dédiée à un seul compte, sans phrase secrète donc stockée uniquement dans le coffre de secrets de la forge, révocable en une opération (retirer sa ligne du fichier authorized_keys), et jamais imprimée dans un journal de pipeline.
Ne prenez pas une empreinte d'hôte sans la vérifier. Une commande comme ssh-keyscan ajoute la clé de n'importe quel serveur qui répond à cette adresse. La bonne pratique est de relever l'empreinte de votre serveur (l'hébergeur l'affiche souvent dans sa console) et de l'écrire dans le known_hosts du pipeline.

Action : prouvez que ce compte n'a aucun privilège.

sudo -l -U deploy-react
ssh -i ~/.ssh/deploy_react deploy-react@app-react.exemple.fr "sudo -n true"

Vérification : sudo -l -U deploy-react répond que l'utilisateur n'est pas autorisé à exécuter sudo, et la seconde commande échoue avec sudo: a password is required : c'est le résultat attendu.

En cas d'erreur : si sudo -l -U deploy-react liste une autorisation, n'allez pas plus loin : une entrée a été ajoutée par erreur, dans /etc/sudoers ou dans /etc/sudoers.d/. Faites-la relire par une seconde personne avant de la retirer.

5. Étape 3 — Déployer une livraison et basculer current

Objectif : publier du nouveau code sans jamais écraser la version qui fonctionne.

La règle tient en une phrase : on n'écrit jamais dans la livraison active. Le pipeline crée un dossier horodaté, y copie les fichiers, puis déplace le lien current — une opération quasi instantanée.

Action : déclarez l'hôte de déploiement sur le poste du pipeline, puis écrivez le script.

Host deploiement-react
    HostName app-react.exemple.fr
    User deploy-react
    IdentityFile ~/.ssh/deploy_react
    IdentitiesOnly yes
#!/usr/bin/env bash
# scripts/deploy-react.sh — exécuté par le pipeline, connecté en deploy-react
set -euo pipefail

APP="/srv/apps/react-app"
STAMP="$(date +%Y%m%d-%H%M%S)"
RELEASE="$APP/releases/$STAMP"

echo "Livraison : $RELEASE"

ssh deploiement-react "mkdir -p '$RELEASE'"
rsync -az --delete ./dist/ deploiement-react:"$RELEASE/dist/"
rsync -az ./server/ ./package.json ./package-lock.json deploiement-react:"$RELEASE/"

ssh deploiement-react "ln -sfn '$RELEASE' '$APP/current'"
ssh deploiement-react "readlink -f '$APP/current'"

set -euo pipefail arrête le script à la première erreur au lieu de continuer dans un état douteux. ln -sfn remplace le lien existant (-f) sans créer de lien imbriqué (-n) : le remplacement est atomique, donc aucun visiteur ne tombe sur un dossier incomplet.

Action : rendez le script exécutable et vérifiez l'ordre des livraisons.

ls -1 /srv/apps/react-app/releases
readlink -f /srv/apps/react-app/current
curl -sI https://app-react.exemple.fr | head -n 1

Vérification : releases/ contient la nouvelle livraison horodatée en plus des précédentes, current pointe vers la plus récente, et le domaine répond 200.

En cas d'erreur : si l'ancienne livraison a disparu, un rsync --delete visait le mauvais dossier : il ne doit jamais cibler releases/ entier, seulement le sous-dossier de la livraison en cours. Si current pointe vers un dossier vide, le lien a été créé avant la copie des fichiers : rétablissez l'ordre — copier, puis basculer.

6. Étape 4 — Migrations MariaDB réversibles

Objectif : modifier le schéma avec un compte dédié, après une sauvegarde, et savoir annuler.

Le code d'une application n'est jamais le seul à changer : le schéma de sa base évolue aussi. Une migration est un fichier SQL versionné avec le code, qui s'exécute une seule fois. Trois comptes distincts existent côté base : user_react lit et écrit les données, migrate_react modifie la structure, et aucun des deux n'administre le serveur MariaDB.

Action : sauvegardez avant de toucher au schéma, puis exécutez la migration.

Sur le serveur en deux temps, jamais en un

mariadb-dump -u migrate_react -p app_react > ~/avant-migration-$(date +%Y%m%d-%H%M).sql
ls -lh ~/avant-migration-*.sql
mariadb -u migrate_react -p app_react < migrations/20261017-ajout-colonne.sql

-p sans valeur affiche une invite : le mot de passe ne se retrouve ni dans l'historique du shell, ni dans la liste des processus. Cette sauvegarde immédiate est votre filet pour les prochaines minutes ; le module 10 en fera une routine complète et vérifiée.

Une migration doit être écrite pour être annulable. Avant de l'exécuter, écrivez la requête inverse (DROP COLUMN annule ADD COLUMN). Une colonne supprimée ne se récupère que depuis la sauvegarde — et si personne n'a testé la restauration, elle n'existe pas vraiment.
Ce qui n'est jamais réversible automatiquement : une suppression de colonne, un changement de type qui tronque des valeurs, une fusion de lignes. Ces opérations exigent une sauvegarde dont la restauration a déjà été testée.

Vérification : le fichier de sauvegarde existe et n'est pas vide, la migration se termine sans erreur, et l'application répond toujours 200 après la modification du schéma.

En cas d'erreur : Access denied signifie que vous avez utilisé user_react au lieu de migrate_react : c'est précisément la séparation attendue. Une migration interrompue à mi-chemin ne se relance pas à l'aveugle : restaurez la sauvegarde, corrigez le script, puis réessayez.

7. Étape 5 — Déclencher, vérifier, revenir en arrière

Objectif : qu'un retour arrière soit un geste connu, rapide et sans surprise.

Le redémarrage n'appartient pas au compte de déploiement. Publier des fichiers ne demande aucun privilège ; faire redémarrer un service, si. Voici ce que cela implique concrètement :

Redémarrage nécessaire après déploiement, par application
ApplicationRedémarrageQui agit
A — React (statique) Aucun : Nginx relit les fichiers Personne
A — API Express Obligatoire : le processus garde l'ancien code en mémoire Administrateur : sudo systemctl restart app-react-api
B — PHP Aucun, mais le cache d'opcodes doit être vidé Administrateur : sudo systemctl reload php8.4-fpm
C — FastAPI / Uvicorn Obligatoire : code et environnement virtuel chargés au démarrage Administrateur : sudo systemctl restart app-python-web
Deux options, à trancher explicitement.
Option A — le référentiel actuel. Les comptes deploy-* n'ont aucun droit sudo : le pipeline s'arrête après la bascule de current et l'administrateur lance le redémarrage. Simple, vérifiable, mais l'automatisation est incomplète de quelques secondes.
Option B — ouvrir un droit étroit. Ajouter une entrée sudoers limitée à une seule commande, /bin/systemctl restart app-react-api.service, puis la tester avec sudo -l -U deploy-react. Le pipeline redémarre lui-même. Le coût est réel : ce droit devient une surface d'attaque, et un motif trop large (par exemple un caractère générique) autoriserait bien plus que prévu.
Choisissez, écrivez le choix, et gardez la trace : une automatisation à moitié documentée est plus dangereuse qu'une automatisation absente.

Action : déployez une modification, vérifiez-la, puis exercez le retour arrière.

ssh deploiement-react "readlink -f /srv/apps/react-app/current"
curl -sI https://app-react.exemple.fr | head -n 1
curl -s https://app-react.exemple.fr/api/health
ls -1 /srv/apps/react-app/releases
ssh deploiement-react "ln -sfn /srv/apps/react-app/releases/20261017-1010 /srv/apps/react-app/current"
ssh deploiement-react "readlink -f /srv/apps/react-app/current"

Le retour arrière ne reconstruit rien et ne restaure rien : il repointe le lien vers une livraison qui a déjà tourné. C'est pourquoi chaque livraison reste sur le disque : les cinq dernières versions réussies sont conservées, ce qui laisse toujours une cible de repli.

Vérification : après la bascule, readlink -f renvoie l'ancienne livraison, le domaine répond de nouveau, et vous savez à quelle version vous êtes revenu. Le retour arrière a été exécuté, pas seulement imaginé.

En cas d'erreur : si l'ancienne livraison a été purgée, le retour arrière est impossible : c'est un incident, pas un détail. Vérifiez la politique de rétention de cinq versions et contrôlez qu'elle est réellement appliquée. Un retour arrière de code ne défait jamais une migration de base : le schéma doit rester compatible avec la version précédente du code.

8. Problèmes courants

Symptôme, cause probable, action.

Problèmes courants : symptôme, cause probable et action
SymptômeCause probableQue faire
Le pipeline déploie mais l'ancien code reste servi Le service n'a pas redémarré, ou current n'a pas bougé readlink -f sur current, puis redémarrage selon le tableau ci-dessus
Permission denied (publickey) Mauvaise clé, ou compte de destination erroné Vérifiez l'hôte déclaré et la ligne correspondante dans authorized_keys
Deux déploiements se marchent dessus Aucune limitation de concurrence Ajoutez un groupe de concurrence, avec annulation de l'exécution précédente
La migration a réussi, l'application échoue Le code déployé ne correspond pas au nouveau schéma Rétablissez la version précédente du code, puis décidez si la migration est annulée
Le disque se remplit après quelques semaines Les livraisons s'accumulent sans purge Vérifiez la rétention sur cinq versions et supprimez les plus anciennes
Un secret apparaît dans les journaux du pipeline Une commande affiche son environnement d'exécution Considérez le secret comme exposé et régénérez-le, puis masquez la sortie

9. Checklist finale

Ce module est terminé lorsque les neuf points suivants sont vrais.

  • Chaque application a son pipeline, avec la même séquence tests, build, déploiement.
  • Le déploiement est impossible depuis une branche de travail.
  • Une clé de déploiement dédiée existe, et sudo -l -U deploy-react ne renvoie aucun droit.
  • Aucune entrée sudoers n'existe pour les comptes deploy-*.
  • Le déploiement crée une livraison horodatée et ne modifie jamais la livraison active.
  • Les migrations utilisent le compte de migration, jamais le compte d'exécution.
  • Une sauvegarde précède chaque migration, et sa restauration a déjà été testée.
  • Le retour arrière a été exécuté au moins une fois, avec succès.
  • Le choix concernant le redémarrage (option A ou B) est écrit et assumé.
Et ensuite ? Le module 10 protège ce que tout ceci fait tourner : les données. Sauvegardes automatiques, restauration vérifiée, et rotation des journaux.
