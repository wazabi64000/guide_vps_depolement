Module 08 · Du code qu'on peut relire

Organiser les dépôts Git et les versions

Trois applications, c'est trois histoires différentes. Ce module range le code en trois dépôts, fixe une convention de branches, sépare les environnements, et fait en sorte qu'aucun mot de passe ne finisse jamais dans l'historique.

Module 08 Aucun déploiement on organise, on ne publie pas encore Prérequis module 06
Un secret poussé dans un dépôt doit être considéré comme compromis. Le retirer ensuite ne suffit pas : l'historique conserve tout. La seule réaction correcte est de régénérer le secret.
Cette page ne mentionne aucune forge particulière comme obligatoire. Les principes valent pour Git lui-même ; les interfaces de relecture varient d'une forge à l'autre et ne sont pas décrites ici.

1. Objectif du module

À la fin de ce module, chaque application a son dépôt, ses branches et ses environnements, et l'historique ne contient aucun secret.

  • Créer un dépôt par application, avec une branche principale unique.
  • Appliquer une convention de nommage pour les branches et les messages de commit.
  • Séparer local, test, préproduction et production.
  • Empêcher tout secret d'entrer dans l'historique.
  • Instaurer une relecture avant intégration sur la branche principale.
Pourquoi un dépôt par application ? Parce que les trois applications se déploient séparément. Un dépôt commun obligerait à déployer les trois ensemble, à chaque fois, même pour corriger une virgule.

2. Prérequis

Ce module travaille sur du code déjà présent.

  • Module 06 : les trois applications tournent sur le serveur.
  • Le code des trois applications est disponible localement ou sur le serveur.
  • Vous savez écrire un fichier .gitignore et lire la sortie de git status.
Avant tout premier commit, vérifiez ce que vous allez versionner. Un dépôt initialisé dans le mauvais dossier versionne des dépendances, un dossier dist/, et parfois le fichier .env réel.

3. Étape 1 — Un dépôt par application

Objectif : trois dépôts indépendants, avec une branche principale explicite.

Action : initialisez le dépôt de l'application A sur votre poste local.

Poste local crée un dépôt

cd ~/projets/react-app
git init -b main
git status

git init -b main crée le dépôt et nomme la branche principale main : plus de doute sur le nom par défaut selon la version de Git installée. git status montre ce qui serait ajouté : lisez-le avant d'ajouter quoi que ce soit.

Vérification : git status indique On branch main et No commits yet. La liste des fichiers non suivis ne contient ni node_modules/, ni dist/, ni .env.

En cas d'erreur : fatal: not a git repository signifie que vous n'êtes pas dans le dossier du projet. Un dépôt créé trop haut (par exemple dans votre dossier personnel) engloberait tous vos projets : supprimez le dossier .git mal placé et recréez-le dans le bon répertoire.

4. Étape 2 — Branches et messages de commit

Objectif : que l'historique explique pourquoi, pas seulement quoi.

Convention de nommage des branches
PréfixeUsageExemple
mainBranche principale, toujours déployable—
feat/Nouvelle fonctionnalitéfeat/ajout-recherche
fix/Correction de bugfix/erreur-connexion-sql
chore/Maintenance sans effet visiblechore/maj-dependances

Action : créez une branche, commitez, puis relisez votre historique.

git switch -c feat/ajout-recherche
git add -A
git commit -m "Ajouter la recherche par nom dans la liste"
git log --oneline -5
git switch main

git switch change de branche : ici, on crée une branche dédiée plutôt que de travailler directement sur main. Un message de commit utile décrit l'intention, pas les fichiers touchés : Git sait déjà quels fichiers ont changé.

Vérification : git log --oneline affiche un message lisible, et git branch montre que vous êtes revenu sur main sans y avoir commité.

En cas d'erreur : user.name and user.email are not set : configurez-les une fois pour toutes avec git config --global user.name et user.email. Un commit envoyé sur main par erreur : créez la branche fix/... à cet endroit et ramenez main au commit précédent, après avoir vérifié que personne d'autre ne l'utilise.

5. Étape 3 — Séparer les environnements

Objectif : que le code sache où il tourne, sans contenir de valeur propre à un environnement.

Les quatre environnements et leur usage
EnvironnementOùDonnées
localVotre posteJeu de données de test, jetable
testIntégration continueBase éphémère, recréée à chaque exécution
préproductionServeur, domaine non publicCopie anonymisée de la production
productionServeur, domaines publicsDonnées réelles — aucune expérimentation

Action : versionnez un modèle de fichier d'environnement, jamais un fichier réel.

DB_HOST=127.0.0.1
DB_PORT=3306
DB_NAME=app_react
DB_USER=user_react
DB_SECRET=remplacer-par-un-secret-local

Enregistrez ce contenu dans .env.example, qui est versionné. Le fichier .env réel, lui, ne l'est jamais : il est recréé sur chaque serveur à partir de ses propres secrets (module 06).

Vérification : .env.example apparaît dans git status comme fichier à ajouter, et son contenu ne permet d'accéder à aucune base réelle : les valeurs sont des exemples.

Une variable compilée dans un build frontend n'est pas un secret. Tout ce qui est intégré au code React part chez le navigateur en clair. Les identifiants SQL restent côté serveur, dans le fichier .env lu par l'application.

6. Étape 4 — Exclure les secrets du versionnement

Objectif : qu'aucun mot de passe, aucune clé privée, ne puisse être committé par accident.

Action : créez le fichier .gitignore à la racine du dépôt.

.env
.env.*
!.env.example
node_modules/
dist/
.venv/
__pycache__/
*.log

En informatique, le ! veut dire « sauf » : la ligne !.env.example réintègre le modèle, alors que tous les autres fichiers d'environnement sont ignorés. dist/ est ignoré parce qu'il est produit par le build : on versionne la recette, pas le gâteau.

Action : prouvez que l'exclusion fonctionne réellement.

touch .env
git check-ignore -v .env
git status --porcelain

Vérification : git check-ignore -v .env affiche la ligne du .gitignore responsable, et git status --porcelain ne mentionne pas .env. Vous pouvez ensuite supprimer le fichier témoin.

En cas d'erreur : si .env apparaît quand même, .gitignore n'est pas à la racine du dépôt, ou le fichier a déjà été suivi par Git : un .gitignore ne s'applique pas aux fichiers déjà suivis.

Si un secret a déjà été poussé : le supprimer au commit suivant ne le retire pas de l'historique. La réaction correcte, dans cet ordre : considérer le secret comme public, le régénérer (base de données, clé SSH, jeton d'accès), puis seulement nettoyer l'historique si nécessaire. Régénérer d'abord : c'est ce qui arrête réellement l'exposition.

7. Étape 5 — Faire relire avant intégration

Objectif : qu'aucune modification n'atteigne la branche principale sans avoir été relue.

Le principe tient en une phrase : on ne pousse pas directement sur main. On pousse la branche feat/... ou fix/..., et on demande une relecture. La branche principale reste toujours dans un état déployable.

Action : déclarez le dépôt distant et envoyez votre branche.

git remote add origin <URL_DU_DEPOT_DISTANT>
git push -u origin main
git push -u origin feat/ajout-recherche

git push -u origin main envoie la branche principale et mémorise sa destination : les envois suivants n'ont plus besoin de préciser la cible.

Vérification : la branche feat/ajout-recherche existe sur le dépôt distant, et main ne contient pas encore vos modifications. La relecture peut commencer.

En cas d'erreur : failed to push some refs signifie que le dépôt distant a des commits que vous n'avez pas : récupérez-les avec git pull --rebase avant de pousser, plutôt que de forcer. Un push --force sur une branche partagée peut effacer le travail d'autrui.

8. Problèmes courants

Symptôme, cause probable, action.

Problèmes courants : symptôme, cause probable et action
SymptômeCause probableQue faire
.env apparaît malgré le .gitignore Le fichier est déjà suivi par Git Retirez-le de l'index, régénérez le secret, puis vérifiez à nouveau
node_modules/ versionné Le .gitignore a été créé après le premier commit Retirez-le de l'index : un dossier déjà suivi n'est plus ignoré
failed to push some refs Le dépôt distant a avancé git pull --rebase, puis poussez à nouveau
Un fichier dist/ modifié apparaît dans chaque commit Le build est versionné alors qu'il est généré Ajoutez dist/ au .gitignore et retirez-le de l'index
Conflit sur .env.example Deux personnes ont ajouté des variables différentes Fusionnez les deux listes : le modèle doit contenir toutes les variables, sans valeurs réelles
Un participant ne peut pas cloner Il utilise son propre compte SSH, ou la mauvaise URL Vérifiez l'URL du dépôt et la clé déclarée sur la forge

9. Checklist finale

Ce module est terminé lorsque les sept points suivants sont vrais.

  • Les trois dépôts existent et portent une branche principale nommée main.
  • La convention de branches est écrite et appliquée.
  • Chaque dépôt contient un .env.example à jour et aucun .env réel.
  • git check-ignore -v .env prouve l'exclusion.
  • git log --all --oneline -- .env ne renvoie rien.
  • Aucune modification n'arrive sur main sans relecture.
  • La règle « un secret exposé se régénère » est connue de toute l'équipe.
Et ensuite ? Le module 09 automatise tout ce qui a été fait à la main : tests, build, déploiement, contrôle de santé et retour arrière.
