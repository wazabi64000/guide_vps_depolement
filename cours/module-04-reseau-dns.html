Module 04 · Faire le lien entre un nom et une machine

Configurer le réseau, les domaines et l'accès distant

Une adresse IP change, un nom ne change pas. Ce module lit la configuration réseau du serveur, rattache trois sous-domaines, puis choisit un moyen d'atteindre la machine depuis l'extérieur — selon que vous êtes sur un VPS ou derrière une box.

Valeurs fictives. 192.0.2.10, 2001:db8::10, 192.0.2.53 et app-react.exemple.fr sont des valeurs réservées à la documentation (RFC 5737, RFC 3849, RFC 2606). Remplacez-les par vos valeurs réelles.
Aucune sortie réelle. Les résultats affichés sont décrits. Ce que vous verrez dépend de votre offre, de votre box et de votre zone DNS.

1. Objectif du module

À la fin de ce module, trois sous-domaines désignent votre serveur, et vous savez diagnostiquer une résolution DNS incorrecte.

  • Lire les interfaces, les routes et les ports en écoute.
  • Distinguer un enregistrement A, AAAA et CNAME.
  • Rattacher app-react, app-php et app-python à votre serveur.
  • Choisir un mode d'accès distant adapté à votre situation.
  • Diagnostiquer un nom qui ne pointe pas au bon endroit.
Un nom de domaine, à quoi ça sert ? À obtenir un certificat HTTPS valide et à garder la même adresse pour vos utilisateurs, même si l'adresse IP change.

2. Prérequis

Ce module suppose deux choses.

  • Vous connaissez l'adresse IP de votre serveur (module 01).
  • Vous avez un nom de domaine et l'accès à l'interface de sa zone DNS.
Serveur à domicile ? Si l'adresse de votre box est privée (192.168.0.0/16, 10.0.0.0/8 ou 172.16.0.0/12), un enregistrement A public ne peut pas la désigner : l'étape 4 traite ce cas.

3. Étape 1 — Lire le réseau du serveur

Objectif : savoir quelles adresses le serveur porte réellement, et où va son trafic.

Action : relevez adresses, routes et ports.

Sur le serveur lecture seule

ip -br address
ip route
ip -6 route
ss -lntup

ip -br address liste vos interfaces en une ligne chacune : lo (boucle locale), l'interface publique, et éventuellement une interface privée. ip route et ip -6 route montrent la passerelle par défaut, une par famille d'adresses.

Vérification : vous savez nommer votre interface publique, son adresse IPv4, son éventuelle adresse IPv6, et la passerelle associée. Notez-les : ce sont les valeurs que vous reporterez dans votre zone DNS.

En cas d'erreur : ip introuvable sur votre poste local est normal sous Windows ou macOS : ces commandes s'exécutent sur le serveur. Pas d'adresse IPv6 affichée : votre offre n'en fournit pas — notez-le comme une limite de l'environnement (module 02 du référentiel), sans en déduire que le serveur est protégé.

4. Étape 2 — Comprendre A, AAAA et CNAME

Objectif : savoir quel type d'enregistrement créer, et pourquoi.

Types d'enregistrements DNS utilisés dans ce cours
TypeContientExemple
Aune adresse IPv4app-react.exemple.fr → 192.0.2.10
AAAAune adresse IPv6app-react.exemple.fr → 2001:db8::10
CNAMEun autre nom (alias)www.exemple.fr → exemple.fr

Un nom peut porter à la fois un A et un AAAA : le navigateur choisit la famille qu'il préfère. C'est précisément pour cela que le serveur doit être correctement filtré dans les deux familles.

Vérification : vous savez dire pourquoi on crée un A (l'adresse IPv4 du serveur) et un AAAA (son adresse IPv6), et pourquoi un CNAME ne se place pas à côté d'un A sur le même nom.

En cas d'erreur : un CNAME et un A sur le même nom entrent en conflit : la zone est invalide et l'interface du fournisseur refuse l'enregistrement. Utilisez un CNAME pour un alias, pas pour le nom principal.

5. Étape 3 — Rattacher les trois sous-domaines

Objectif : que chaque application ait son propre nom.

Action : dans l'interface de votre zone DNS, créez six enregistrements (un A et, si vous avez IPv6, un AAAA par nom).

Les trois sous-domaines à créer
NomTypeValeurApplication
app-react.exemple.frA + AAAA192.0.2.10 · 2001:db8::10A — React + Express
app-php.exemple.frA + AAAAmêmes adressesB — PHP + PDO
app-python.exemple.frA + AAAAmêmes adressesC — FastAPI + Uvicorn

Action : vérifiez la propagation depuis votre poste local.

getent hosts app-react.exemple.fr
getent hosts app-php.exemple.fr
getent hosts app-python.exemple.fr

Le TTL (durée de vie) de chaque enregistrement décide du temps de propagation : gardez une valeur courte (par exemple 300 secondes) pendant la mise en place, vous pourrez l'augmenter ensuite.

Vérification : les trois commandes renvoient l'adresse de votre serveur. Si un AAAA existe, la même vérification doit montrer une adresse IPv6.

En cas d'erreur : getent ne renvoie rien tant que la zone n'est pas publiée : attendez le TTL, videz le cache local si votre système en a un, puis réessayez. Une faute de frappe dans le sous-domaine crée un nom qui n'existe pas : recopiez-le depuis votre tableau, jamais de mémoire.

6. Étape 4 — Choisir un mode d'accès distant

Objectif : décider, par ordre de sécurité, comment la machine sera joignable.

Modes d'accès distant, du plus sûr au plus exposé
ModeQuand l'utiliserCe qu'il implique
1. Réseau local seulementLe plus sûr : aucun port publiéAccessible uniquement depuis chez vous
2. VPN (ex. WireGuard)Vous voulez y accéder de partout, sans rien publierUn tunnel : le serveur se comporte comme s'il était local
3. Publication webVous voulez un vrai site publicRedirection de port, DNS, HTTPS, pare-feu : tout doit être vérifié

Action : sur un serveur à domicile, déterminez si vous êtes derrière un partage d'adresse (CGNAT).

Poste local lecture seule

ip -br address

Si l'adresse publique que vous voyez depuis Internet n'est pas celle de votre box, votre opérateur partage une adresse : la plage concernée est 100.64.0.0/10 (RFC 6598). Dans ce cas, la redirection de port IPv4 est souvent impossible : préférez l'option 2 (VPN) ou une IPv6 correctement filtrée.

Vérification : le mode d'accès est choisi et écrit. Pour un serveur à domicile, vous savez dire si vous êtes derrière un CGNAT, et vous avez une solution de repli si la redirection de port est indisponible.

Ce qui ne doit jamais être publié. La base de données, l'outil d'administration SQL et les ports internes des applications. La publication web ne concerne que 80 et 443 (module 03).

7. Étape 5 — Diagnostiquer une résolution DNS

Objectif : en cas de problème, savoir à quelle étape la chaîne casse.

Action : interrogez successivement votre résolveur, puis un autre.

Poste local lecture seule

cat /etc/resolv.conf
getent hosts app-react.exemple.fr
dig +short A app-react.exemple.fr
dig +short AAAA app-react.exemple.fr
dig app-react.exemple.fr @192.0.2.53

Prérequis de cette vérification : dig vient d'un paquet à installer sur votre poste (sous Debian, nommez-le bind9-dnsutils ou dnsutils selon la version — vérifiez avec apt-cache search). getent et cat sont, eux, toujours disponibles.

/etc/resolv.conf montre quel résolveur votre machine interroge. Le second argument de dig (ici 192.0.2.53, une adresse de test) interroge un autre résolveur : si la réponse diffère, le problème vient de la propagation ou du cache, pas de votre zone.

Vérification : les réponses sont identiques quel que soit le résolveur interrogé, et celles de A et AAAA correspondent aux adresses du serveur.

En cas d'erreur : trois résultats se distinguent nettement. NXDOMAIN : le nom n'existe pas (faute de frappe ou enregistrement absent). Une adresse inattendue : l'enregistrement pointe ailleurs (ancienne IP, serveur web de l'hébergeur). Un délai puis no servers could be reached : c'est votre résolveur qui ne répond pas, pas la zone.

8. Problèmes courants

Symptôme, cause probable, action.

Problèmes courants : symptôme, cause probable et action
SymptômeCause probableQue faire
Le nom renvoie une autre adresse Enregistrement créé avant un changement d'IP, ou TTL long encore en cache Corrigez l'enregistrement, attendez le TTL, interrogez un autre résolveur
Le nom résout mais le site ne répond pas Ce n'est plus un problème DNS : rien n'écoute encore sur 80/443 Ce point est traité aux modules 05 et 07
Fonctionne en IPv4, échoue en IPv6 Enregistrement AAAA absent, faux, ou IPv6 filtrée Vérifiez dig +short AAAA et le pare-feu (module 03)
Redirection de port impossible sur la box Adresse partagée par l'opérateur (CGNAT, plage 100.64.0.0/10) Passez au VPN, ou utilisez une IPv6 correctement filtrée
La zone DNS refuse l'enregistrement CNAME en conflit avec un A sur le même nom Un seul type par nom : utilisez CNAME pour un alias
Le nom ne résout que sur certains réseaux Serveur DNS local filtrant, ou résolveur d'entreprise imposé Comparez avec un résolveur externe pour isoler la cause

9. Checklist finale

Ce module est terminé lorsque les six points suivants sont vrais.

  • Vous savez nommer l'interface publique du serveur, son IPv4, son IPv6 et sa passerelle.
  • Les trois sous-domaines renvoient vers votre serveur.
  • Si IPv6 est disponible, un enregistrement AAAA existe pour chacun.
  • Le mode d'accès distant (local, VPN ou publication) est décidé et écrit.
  • Vous savez quelle commande exécuter pour prouver qu'un nom résout correctement.
  • Aucune base de données ni interface d'administration n'a été publiée sur Internet.
Et ensuite ? Le module 05 installe la pile partagée : Nginx, les runtimes, MariaDB liée à la boucle locale, et phpMyAdmin accessible uniquement par tunnel SSH.
