Module 05 · Installer la pile partagée

Installer Nginx, MariaDB et phpMyAdmin

Les trois applications partageront un serveur web, une base de données et un outil d'administration. Ce module installe le socle, crée une base et deux comptes SQL par application, et garde l'administration hors d'Internet.

Module 05 Installe des paquets et crée des bases Prérequis modules 02 et 03
Rien de ce qui est installé ici ne doit s'exposer publiquement. Ni la base de données, ni l'outil d'administration SQL. Le serveur web, lui, sera publié plus tard (module 07), et seulement sur 80 et 443.
Aucun mot de passe dans cette page. Les blocs copiables contiennent des emplacements (<MOT_DE_PASSE_EXECUTION>) que vous remplacez par des secrets générés localement. Ne collez jamais un mot de passe réel dans un texte copié depuis une page web.

1. Objectif du module

À la fin de ce module, les runtimes sont installés, une base et deux comptes SQL existent par application, et phpMyAdmin n'est joignable que depuis le serveur.

  • Installer Nginx, PHP-FPM, Python et Node.js.
  • Installer MariaDB depuis les paquets Debian et la lier à la boucle locale.
  • Créer trois bases, trois comptes d'exécution et trois comptes de migration.
  • Installer phpMyAdmin sans l'exposer, et préparer l'accès par tunnel SSH.
  • Vérifier qu'aucun service interne n'écoute sur une adresse publique.
Deux comptes SQL par application, pourquoi ? Le compte d'exécution lit et écrit des données ; le compte de migration peut modifier la structure, mais n'est utilisé que pendant un déploiement. L'application qui tourne n'a jamais besoin de supprimer une table.

2. Prérequis

Deux modules doivent être terminés.

  • Module 02 : le système est administré et à jour.
  • Module 03 : l'accès est durci et le pare-feu n'ouvre que 22, 80 et 443.
  • Vous savez générer un secret aléatoire : openssl rand -base64 24.
Notez chaque secret dans un gestionnaire de mots de passe au moment où vous le générez. Un mot de passe de base de données perdu se régénère ; un mot de passe perdu pendant une migration vous coûte une soirée.

3. Étape 1 — Installer Nginx, PHP-FPM et Python

Objectif : disposer du serveur web et des deux runtimes côté serveur.

Action : installez les paquets Debian.

Sur le serveur installe des paquets

sudo apt install nginx php-fpm python3-venv python3-pip
nginx -v
php -v
python3 --version
systemctl status nginx --no-pager

nginx -v, php -v et python3 --version affichent les versions effectivement installées par Debian : ce sont elles qui comptent, pas la dernière version publiée en amont. Notez-les : les chemins de configuration en dépendent (par exemple /etc/php/8.4/ pour PHP 8.4).

Vérification : les trois versions s'affichent et systemctl status nginx indique active (running). Le numéro du dossier /etc/php/<version>/ correspond à la version affichée par php -v.

En cas d'erreur : nginx -v introuvable ou nginx: command not found signifie que le paquet n'est pas installé : relancez sudo apt install nginx et lisez le message d'erreur. Unable to locate package : commencez par sudo apt update (module 02).

4. Étape 2 — Node.js pour l'application React + Express

Objectif : exécuter l'API Express en Node.js, avec une version adaptée.

Action : installez Node.js depuis Debian, puis relevez la version.

Sur le serveur installe des paquets

sudo apt install nodejs npm
node -v
npm -v

Le paquet Debian est maintenu et corrigé, mais il peut être plus ancien que la version LTS publiée par le projet. Comparez node -v avec la LTS annoncée sur nodejs.org : si votre application exige une version plus récente, suivez les instructions officielles du projet Node.js — jamais un tutoriel trouvé au hasard.

Vérification : node -v et npm -v répondent tous les deux. Notez la version obtenue : elle sera rappelée au module 06 pour le service Express.

En cas d'erreur : node: command not found après l'installation : vérifiez que vous êtes bien sur le serveur et non sur votre poste. N'installez jamais deux Node.js en parallèle (paquet Debian et une installation manuelle) : les chemins deviennent imprévisibles au moment où un service systemd démarre.

5. Étape 3 — Installer MariaDB et la lier à la boucle locale

Objectif : une seule instance MariaDB, joignable uniquement depuis le serveur lui-même.

Action : installez depuis les paquets Debian, puis sécurisez l'installation.

Sur le serveur installe des paquets

sudo apt install mariadb-server
mariadb --version
sudo mariadb-secure-installation

mariadb-secure-installation vous guide pour supprimer les comptes anonymes et interdire la connexion distante du compte d'administration. Acceptez les réglages proposés : ils vont dans le sens de ce cours.

Action : vérifiez qu'elle n'écoute que sur la boucle locale.

sudo grep -R bind-address /etc/mysql/
sudo ss -lntp

bind-address doit valoir 127.0.0.1. Dans la sortie de ss -lntp, cherchez la ligne de MariaDB : l'adresse d'écoute doit être 127.0.0.1, jamais une interface publique.

Vérification : le fichier de configuration déclare bind-address = 127.0.0.1, et ss -lntp ne montre MariaDB que sur la boucle locale. Le pare-feu (module 03) ne comporte aucune règle l'autorisant depuis Internet.

Ne modifiez jamais bind-address vers 0.0.0.0. Ce réglage publierait la base sur toutes les interfaces réseau, y compris IPv6. Un port fermé en IPv4 ne suffit pas : vérifiez toujours l'écoute complète avec ss -lntp.

En cas d'erreur : Access denied en local vient souvent d'un mot de passe de compte d'administration défini par le paquet. Sur Debian, l'administration locale passe par le socket Unix : sudo mariadb fonctionne sans mot de passe, ce qui est le comportement attendu.

6. Étape 4 — Trois bases, six utilisateurs SQL

Objectif : chaque application a sa base et deux comptes, au moindre privilège.

Action : générez six secrets sur le serveur, un par compte.

openssl rand -base64 24

Action : ouvrez la console SQL et créez les trois bases.

Sur le serveur crée des bases

sudo mariadb
CREATE DATABASE app_react  CHARACTER SET utf8mb4 COLLATE utf8mb4_unicode_ci;
CREATE DATABASE app_php    CHARACTER SET utf8mb4 COLLATE utf8mb4_unicode_ci;
CREATE DATABASE app_python CHARACTER SET utf8mb4 COLLATE utf8mb4_unicode_ci;

Action : créez les deux comptes de l'application A, puis les privilèges correspondants.

CREATE USER 'user_react'@'localhost'    IDENTIFIED BY '<MOT_DE_PASSE_EXECUTION>';
CREATE USER 'migrate_react'@'localhost' IDENTIFIED BY '<MOT_DE_PASSE_MIGRATION>';

GRANT SELECT, INSERT, UPDATE, DELETE
  ON app_react.* TO 'user_react'@'localhost';

GRANT SELECT, INSERT, UPDATE, DELETE, CREATE, ALTER, DROP, INDEX, REFERENCES
  ON app_react.* TO 'migrate_react'@'localhost';

FLUSH PRIVILEGES;

Répétez ce bloc pour php (base app_php) puis pour python (base app_python), en remplaçant les noms et les mots de passe. Aucun GRANT ALL, aucune portée *.* : chaque compte ne voit que sa base.

Vérification : SHOW DATABASES; liste les trois bases et SELECT user, host FROM mysql.user; montre les six comptes attendus. Chaque user_* n'a que quatre droits, sur une seule base.

En cas d'erreur : Access denied for user ... to database 'app_php' est le comportement attendu si vous testez un compte sur la base d'une autre application : c'est la séparation qui fonctionne. ERROR 1396 signifie que le compte existe déjà : utilisez ALTER USER plutôt que CREATE USER.

7. Étape 5 — phpMyAdmin accessible par tunnel SSH

Objectif : administrer la base depuis son navigateur, sans jamais l'exposer sur Internet.

Action : installez phpMyAdmin, puis créez un accès local.

Sur le serveur installe des paquets

sudo apt install phpmyadmin

Refusez la configuration automatique du serveur web pendant l'installation : nous écrivons nous-mêmes un hôte qui n'écoute que sur la boucle locale, sur un port réservé. 

sudoedit /etc/nginx/sites-available/phpmyadmin-local.conf
server {
    listen 127.0.0.1:8443;
    server_name localhost;

    root /usr/share/phpmyadmin;
    index index.php;

    location ~ \.php$ {
        include snippets/fastcgi-php.conf;
        fastcgi_pass unix:/run/php/app-pma.sock;
    }
}

Action : créez un pool PHP-FPM dédié, avec un compte sans droits sur les applications.

sudoedit /etc/php/8.4/fpm/pool.d/app-pma.conf
[app-pma]
user = svc-php
group = phpapp
listen = /run/php/app-pma.sock
listen.owner = www-data
listen.group = www-data
pm = dynamic
pm.max_children = 5

Action : activez l'hôte, testez, rechargez.

sudo ln -s /etc/nginx/sites-available/phpmyadmin-local.conf /etc/nginx/sites-enabled/
sudo nginx -t
sudo systemctl reload nginx
sudo systemctl restart php8.4-fpm

Action : depuis votre poste local, ouvrez le tunnel.

Poste local ouvre un tunnel

ssh -L 8443:127.0.0.1:8443 admin@192.0.2.10

Laissez cette fenêtre ouverte, puis ouvrez http://localhost:8443 dans votre navigateur : le trafic passe par SSH, chiffré, sans qu'aucun port ne soit ouvert sur Internet.

Vérification : nginx -t valide la configuration, et l'authentification de phpMyAdmin est de type cookie. Depuis l'extérieur, l'adresse 192.0.2.10:8443 doit être injoignable.

En cas d'erreur : une erreur 500 vient souvent d'un dossier temporaire non inscriptible par le compte du pool : vérifiez les droits de /var/lib/phpmyadmin et de son sous-dossier tmp. 502 Bad Gateway signifie que le socket PHP-FPM n'existe pas : contrôlez que le pool est bien chargé et que le chemin du socket est identique dans les deux fichiers. Adaptez 8.4 si votre php -v affiche une autre version.

8. Problèmes courants

Symptôme, cause probable, action.

Problèmes courants : symptôme, cause probable et action
SymptômeCause probableQue faire
502 Bad Gateway sur phpMyAdmin Le socket PHP-FPM n'existe pas ou porte un autre nom Comparez listen du pool et fastcgi_pass de l'hôte
erreur 500 sur phpMyAdmin Dossier temporaire non inscriptible par le compte du pool Contrôlez les droits de /var/lib/phpmyadmin
Access denied for user en SQL Mauvais compte, mauvais mot de passe, ou base d'une autre application Vérifiez le nom exact du compte et sa portée avec SHOW GRANTS
Can't connect to local server through socket MariaDB n'est pas démarrée systemctl status mariadb puis journalctl -u mariadb
Le tunnel SSH refuse le port local Le port 8443 est déjà utilisé sur votre poste Choisissez un autre port local : -L 9443:127.0.0.1:8443
Un service apparaît sur une adresse publique Il n'a pas été lié à la boucle locale Corrigez son fichier de configuration, pas le pare-feu

9. Checklist finale

Ce module est terminé lorsque les sept points suivants sont vrais.

  • Nginx, PHP-FPM, Python et Node.js sont installés, et leurs versions sont notées.
  • MariaDB est installée depuis les paquets Debian et liée à 127.0.0.1.
  • Les trois bases app_react, app_php et app_python existent.
  • Six comptes SQL existent, chacun limité à sa base, sans aucun GRANT ALL.
  • Les six secrets sont enregistrés dans un gestionnaire de mots de passe, et nulle part dans une page web.
  • phpMyAdmin n'écoute que sur la boucle locale et n'est joignable que par tunnel SSH.
  • Le pare-feu n'a été modifié pour aucun de ces services internes.
Et ensuite ? Le module 06 met les applications en ligne localement : comptes distincts, services systemd, pool PHP-FPM dédié et environnement virtuel Python.
