Module 10 · Ce qui doit survivre

Sauvegarder et restaurer

Tout le reste du parcours suppose que les données existent encore demain. Ce module décide ce qui doit survivre, automatise les copies, les sort du serveur — et prouve qu'elles sont restaurables.

Module 10 Sort de la machine une copie qui n'y est pas ne survivra pas Prérequis module 05
Une sauvegarde jamais restaurée n'est pas une sauvegarde. C'est une croyance. Tant que vous n'avez pas remis les données en place depuis la copie, vous ne savez rien de son contenu, ni de sa lisibilité, ni de sa complétude.

1. Objectif du module

À la fin de ce module, les données des trois applications quittent le serveur chaque nuit, sous forme chiffrée, et vous avez déjà réussi à les remettre en place.

  • Lister ce qui est irremplaçable, et ce qui se reconstruit tout seul.
  • Extraire chaque base MariaDB sans interrompre le service.
  • Archiver les configurations et les fichiers de secrets.
  • Automatiser par minuterie systemd, avec rétention.
  • Prouver la restauration sur une base de test, puis nettoyer.
La règle des trois copies. Trois exemplaires, sur deux supports différents, dont un hors du serveur. Un serveur qui sauvegarde ses données sur son propre disque ne se sauvegarde pas : il les rassemble.

2. Prérequis

Trois éléments déjà en place rendent ce module possible.

  • Module 05 : les trois bases et leurs comptes existent, MariaDB n'écoute qu'en local.
  • Module 06 : les fichiers d'environnement sont en shared/, lisible par le service uniquement.
  • Un espace de destination existe en dehors du serveur (machine personnelle, stockage distant, second serveur).
Vérifiez l'espace disponible avant de commencer. Une sauvegarde qui échoue faute de place laisse souvent un fichier tronqué à la place d'une erreur visible : le pire des cas est une copie partielle qu'on croit complète.

3. Étape 1 — Décider ce qui doit survivre

Objectif : savoir, pour chaque élément, s'il se reconstruit ou s'il est unique.

Ce qui doit être sauvegardé, et ce qui se reconstruit
ÉlémentUnique ?Pourquoi
Les trois bases MariaDB Oui Données créées par les utilisateurs : irremplaçables
Fichiers d'environnement shared/.env Oui Mots de passe et clés : sans eux, l'application ne démarre pas
Configurations serveur (Nginx, PHP-FPM, unités systemd) Oui Des heures de réglages : reproductibles, mais coûteux
Le code des applications Non Il vit dans Git (module 08) : le dépôt est la copie
Dépendances installées, caches, environnements virtuels Non Se réinstallent à partir des fichiers de dépendances
Certificats TLS Presque Se réobtiennent avec Certbot, mais sauvegarder /etc/letsencrypt évite de retomber sur les limites de l'autorité

Vérification : vous savez répondre à la question « si le disque meurt maintenant, qu'est-ce que je ne peux plus reconstruire ? » et la liste tient en trois lignes.

Sauvegarder tout n'est pas sauvegarder bien. Copier des caches et des dépendances multiplie le volume, allonge la durée, et rend la sauvegarde plus difficile à restaurer. Ce qui compte, c'est l'irremplaçable.

4. Étape 2 — Sauvegarder les trois bases MariaDB

Objectif : obtenir un fichier SQL complet, sans bloquer les applications.

Action : créez le dossier de sauvegarde, puis extrayez la base de l'application A.

Sur le serveur lecture seule des données

sudo install -d -m 750 -o root -g root /var/backups/mariadb
mariadb-dump --single-transaction --routines --events \
  -u migrate_react -p app_react | gzip > /tmp/app_react-$(date +%F).sql.gz
ls -lh /tmp/app_react-$(date +%F).sql.gz

--single-transaction lit les tables InnoDB dans un état cohérent sans verrouiller la base : les visiteurs continuent d'écrire pendant l'extraction. --routines et --events incluent les procédures et les tâches planifiées, que l'option par défaut omet. Le tube | gzip compresse à la volée : le fichier intermédiaire en clair n'existe jamais sur le disque.

Le compte utilisé doit pouvoir lire. Le compte de migration porte les droits de structure ; vérifiez qu'il dispose aussi de SELECT sur sa base : sudo mariadb -e "SHOW GRANTS FOR 'migrate_react'@'localhost';". Si ce n'est pas le cas, n'ajoutez pas un compte d'administration SQL : ajustez les droits de ce compte-ci, sur cette base uniquement.

Action : répétez pour les deux autres bases.

mariadb-dump --single-transaction --routines --events \
  -u migrate_php -p app_php | gzip > /tmp/app_php-$(date +%F).sql.gz
mariadb-dump --single-transaction --routines --events \
  -u migrate_python -p app_python | gzip > /tmp/app_python-$(date +%F).sql.gz
ls -lh /tmp/*.sql.gz

Vérification : les trois fichiers existent, leur taille est non nulle, et elle est comparable à celle du dump de la veille. Un fichier qui passe de 40 Mo à 2 Ko signale une extraction vide, pas une base plus légère.

En cas d'erreur : Access denied : mauvais compte ou mauvais mot de passe. Unknown database : nom de base erroné, vérifiez avec sudo mariadb -e "SHOW DATABASES;". Un fichier vide avec set -e : le script continue alors que le dump a échoué — c'est pour cela qu'on vérifie la taille.

5. Étape 3 — Archiver configurations et secrets

Objectif : pouvoir reconstruire un serveur identique sans rien deviner.

Action : réunissez les fichiers qui décrivent votre serveur.

sudo install -d -m 750 /var/backups/config
sudo tar czf /var/backups/config/config-$(date +%F).tar.gz \
  /etc/nginx/sites-available \
  /etc/php/8.4/fpm/pool.d \
  /etc/mysql/mariadb.conf.d \
  /etc/systemd/system/app-react-api.service \
  /etc/systemd/system/app-python-web.service \
  /etc/ssh/sshd_config \
  /etc/letsencrypt \
  /srv/apps/react-app/shared \
  /srv/apps/php-app/shared \
  /srv/apps/python-app/shared
sudo tar tzf /var/backups/config/config-$(date +%F).tar.gz | head

tar retire le / initial des chemins : l'archive se restaure donc relativement là où vous l'extrairez. C'est volontaire — et cela signifie qu'une restauration se fait depuis la racine, en connaissance de cause.

Cette archive contient vos secrets. Les fichiers shared/.env portent des mots de passe, /etc/letsencrypt porte une clé privée TLS. En clair, cette archive est aussi sensible que le serveur lui-même : elle ne doit jamais être déposée sur un espace partagé ou un envoi de fichiers public. Le chiffrement de l'étape 4 n'est pas une option.

Vérification : tar tzf liste les chemins de l'archive ; vous y reconnaissez vos fichiers de configuration et vos trois fichiers .env.

En cas d'erreur : tar: Exiting with failure status due to previous errors accompagné de Permission denied signifie qu'une commande tar a été lancée sans privilèges sur des fichiers root. Sur Debian 13, le chemin PHP exact est /etc/php/8.4/ : si votre version diffère, adaptez le chemin d'après ls /etc/php/.

6. Étape 4 — Automatiser, chiffrer, sortir du serveur

Objectif : que la sauvegarde se fasse sans vous, et que la copie quitte la machine.

Action : écrivez le script exécuté par la minuterie.

#!/usr/bin/env bash
# /usr/local/sbin/sauvegarde.sh — exécuté par root, chaque nuit
set -euo pipefail

DEST=/var/backups
JOUR="$(date +%F)"

for base in app_react app_php app_python; do
  compte="migrate_${base#app_}"
  mariadb-dump --single-transaction --routines --events \
    --defaults-extra-file=/root/.sauvegarde.cnf "$base" \
    | gzip > "$DEST/mariadb/${base}-${JOUR}.sql.gz"
done

tar czf "$DEST/config/config-${JOUR}.tar.gz" /etc/nginx/sites-available /srv/apps

gpg --batch --yes --symmetric --cipher-algo AES256 \
    --passphrase-file /root/.clef-sauvegarde \
    --output "$DEST/config/config-${JOUR}.tar.gz.gpg" \
    "$DEST/config/config-${JOUR}.tar.gz"
rm -f "$DEST/config/config-${JOUR}.tar.gz"

find "$DEST/mariadb" -name '*.sql.gz' -mtime +7 -delete
find "$DEST/config" -name '*.gpg' -mtime +30 -delete

Le fichier /root/.sauvegarde.cnf (mode 600, propriétaire root) contient les identifiants sous forme de section [client] : la minuterie n'a ainsi aucune invite à laquelle répondre. find -mtime +7 -delete supprime les extractions de plus de sept jours : sans cette purge, le disque se remplit et la sauvegarde finit par échouer en silence.

La clé de chiffrement ne doit pas vivre sur la machine qu'elle protège. Si /root/.clef-sauvegarde n'existe que sur le serveur, alors le jour où le serveur disparaît, vous conservez des archives parfaitement illisibles. Copiez la clé sur votre poste et dans un coffre de secrets, avant la première sauvegarde chiffrée.

Action : déclarez la minuterie systemd, puis activez-la.

[Unit]
Description=Sauvegarde des bases et des configurations

[Service]
Type=oneshot
User=root
ExecStart=/usr/local/sbin/sauvegarde.sh
[Unit]
Description=Déclenche la sauvegarde chaque nuit

[Timer]
OnCalendar=*-*-* 02:30:00
Persistent=true

[Install]
WantedBy=timers.target
sudo systemctl daemon-reload
sudo systemctl enable --now sauvegarde.timer
systemctl list-timers sauvegarde.timer --no-pager
sudo systemctl start sauvegarde.service
sudo journalctl -u sauvegarde.service --no-pager -n 20

Persistent=true rattrape une exécution manquée : si le serveur était éteint à 2 h 30, la sauvegarde se lance au redémarrage. La lancer une fois à la main (start) permet de lire immédiatement les erreurs dans le journal plutôt que de les découvrir trois semaines plus tard.

Vérification : list-timers affiche la prochaine exécution, et journalctl -u sauvegarde.service ne montre aucune erreur. Contrôlez ensuite la sortie réelle : trois fichiers .sql.gz du jour et une archive .gpg.

En cas d'erreur : une minuterie activée mais aucun fichier produit se diagnostique dans journalctl -u sauvegarde. Un échec silencieux est le principal danger : ajoutez un contrôle qui crie lorsqu'une sauvegarde manque, plutôt que de compter sur votre mémoire.

Enfin, sortez la copie du serveur. Transférez les fichiers vers une machine que vous contrôlez, ou un stockage distant, avec rsync sur une connexion chiffrée — jamais par un envoi de fichiers ouvert au public.

7. Étape 5 — Restaurer pour de vrai

Objectif : remettre les données en place, sur une base de test, et vérifier leur contenu.

Une restauration se fait sur une base de test, jamais directement sur la production : si vous écrasez une base vivante avec une sauvegarde incomplète, vous transformez une panne réparable en perte définitive.

Action : créez une base de travail, injectez le dump, contrôlez, puis nettoyez.

Sur le serveur base de test temporaire

sudo mariadb -e "DROP DATABASE IF EXISTS app_react_restauration;"
sudo mariadb -e "CREATE DATABASE app_react_restauration;"
zcat /var/backups/mariadb/app_react-$(date +%F).sql.gz \
  | sudo mariadb app_react_restauration
sudo mariadb -e "SHOW TABLES FROM app_react_restauration;"
sudo mariadb -e "DROP DATABASE app_react_restauration;"

sudo mariadb suffit pour administrer le serveur local : sur Debian, le compte root de MariaDB s'authentifie par le socket local, sans mot de passe. C'est aussi pourquoi aucune administration SQL distante n'est possible : il n'existe pas de root de MariaDB joignable par le réseau. Les applications utilisent leurs trois comptes limités ; vous, vous passez par le socket.

Vérification : SHOW TABLES liste bien vos tables, sans erreur, et la restauration s'est terminée sans message. Comparez le nombre de lignes d'une table connue entre production et restauration : le contenu doit correspondre à la date de la sauvegarde.

En cas d'erreur : ERROR 1046 (No database selected) : la base cible manque après le |. Un gzip: unexpected end of file signale une archive tronquée : la sauvegarde est inutilisable, et il faut le savoir maintenant, pas le jour de l'incident. ERROR 1044 (Access denied) : vous n'utilisez pas le socket local avec les droits d'administration.

L'exercice à refaire régulièrement : simuler la perte complète d'un serveur et reconstruire les trois applications à partir des seuls dépôts Git, des archives de configuration et des dumps. Tout ce qui manque à ce moment-là est exactement ce que votre sauvegarde ne couvrait pas. Les cinq dernières livraisons conservées (module 06) complètent ce dispositif pour un retour arrière rapide.

8. Problèmes courants

Symptôme, cause probable, action.

Problèmes courants : symptôme, cause probable et action
SymptômeCause probableQue faire
Aucun fichier produit dans la nuit La minuterie n'est pas active, ou le script échoue au premier pas systemctl list-timers puis journalctl -u sauvegarde
Fichier de taille quasi nulle Extraction vide : mauvais nom de base, ou échec masqué Vérifiez le nom de la base et la présence de SELECT pour ce compte
Le disque se remplit Purge absente ou trop permissive Contrôlez les règles de rétention et le volume de chaque extraction
gpg: decryption failed Mauvaise clé, ou archive corrompue Testez la clé conservée hors du serveur, avant d'en avoir besoin
Restauration incomplète Le dump a été interrompu, ou les procédures et événements manquaient Réextrayez avec --routines --events et vérifiez la fin du fichier
La sauvegarde contient des données personnelles en clair Archive non chiffrée déposée sur un espace partagé Retirez-la, considérez les données comme exposées, et chiffrez systématiquement

9. Checklist finale

Ce module est terminé lorsque les neuf points suivants sont vrais.

  • La liste de ce qui est irremplaçable est écrite et tient en trois lignes.
  • Les trois bases produisent une extraction quotidienne non vide.
  • Les configurations et les secrets sont archivés.
  • Les archives contenant des secrets sont chiffrées.
  • La clé de chiffrement existe hors du serveur.
  • Une copie des sauvegardes quitte le serveur.
  • La rétention est en place : sept extractions quotidiennes, un mois d'archives.
  • Une restauration a été réussie sur une base de test, puis nettoyée.
  • Un script de contrôle prévient lorsqu'une sauvegarde manque.
Et ensuite ? Le module 11 apprend à voir venir les problèmes : lire les journaux, repérer un service qui boucle, et diagnostiquer avant l'incident.
